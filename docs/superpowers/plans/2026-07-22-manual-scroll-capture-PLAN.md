# Plan: Manual Scroll Capture

_Locked via grill-with-docs — by Claude + Bruno. Terms per CONTEXT.md. Revision 6 (post Codex round 5; round-5 finding accepted post-cap, see PLAN-REVIEW-LOG.md)._

## Goal

Add **Manual Scroll Capture**: the person selects a region with the Selection Overlay, Confirms into scroll mode, and scrolls the content themselves (up or down, in any app, at a pace that keeps consecutive samples overlapping — fast flicks degrade visibly, see Risks). The app repeatedly samples the region and Stitches novel rows into one tall image. A Scroll HUD shows the stitched height with Done/Cancel. The result persists and publishes exactly like today's Auto Scrolling Capture (kind `.scrolling`, opens in the editor). Auto Scrolling Capture stays untouched.

## Approach

1. **Model plumbing** (pattern per existing modes):
   - `CaptureMode.scrollingManual` ("Scroll Area") in `Models.swift`; `CaptureIntent.scrollingAreaSelection`; new `CaptureIntentHandling.beginManualScrollCapture` in `CaptureController.swift`; new `CaptureOperationScope` token case.
   - `ShortcutAction.scrollingManual`, default ⌃⌥⇧S, UserDefaults-backed like the other six actions in `ShortcutPreference.swift`. Rail button added in `MacContentView.swift`.
   - Reuse `CaptureKind.scrolling` for the persisted record — the artifact is the same kind of thing; the library does not distinguish how it was produced.

2. **Selection phase**: reuse the existing area Selection Overlay flow (drag, 8-handle resize, Esc cancel), with a per-intent capability flag passed into the overlay that hides/disables the Quick Annotation toolbar for this intent (annotation coordinates are meaningless against a not-yet-known tall canvas). Test: manual-scroll intent shows no annotation tools. On Confirm, do NOT capture once; transition to scroll mode via the seed barrier (step 3).

3. **Scroll-mode entry — ordered, race-free**:
   1. On Confirm, resolve the **target application**: topmost window (via `CGWindowListCopyWindowInfo`, on-screen, excluding TakeAShot's own windows) whose bounds contain the selected region's **center** — center-only targeting is the defined behavior for selections spanning multiple windows. AppKit-global → Quartz coordinate conversion goes through a pure, unit-tested helper (y-flip about the primary display height). Owner PID → `NSRunningApplication`. Fallback if none resolves: the frontmost application recorded before the Selection Overlay appeared.
   2. **Seed transaction (awaited)**: capture the seed frame of the selected region via the async `ScreenshotCapturing` path (own windows excluded — step 5) and commit it to the session BEFORE any HUD/border appears. Failure → session fails with the standard capture-error alert, full teardown, no scroll mode. Cancellation during the seed → clean abort, nothing persisted. This guarantees the initial viewport is never lost to early scrolling.
   3. Tear down the dimmed Selection Overlay; show the border window (drawn just outside the rect where space allows, may clamp inside at display edges — harmless, it is excluded from capture) — fully click-through (`ignoresMouseEvents = true`).
   4. Show the Scroll HUD as a non-activating panel (`NSPanel` with `.nonactivatingPanel`): live stitched pixel height, Done and Cancel buttons. Placement via a new pure function following the `SelectionToolbarPlacement` pattern (`CaptureGeometry.swift`) + unit tests.
   5. Revalidate the target immediately before activation (PID still running, window still present); then activate the resolved target application so scroll events reach the content being captured. If revalidation fails, the failure is NEVER silent: activation is skipped and the HUD immediately shows an explicit "target changed — click the content to focus" notice; no degraded-counter penalty accrues while frames stay unchanged. The person scrolling after the notice is the explicit go-ahead; otherwise they cancel. (A vanished target produces unchanged/unmatchable frames — no growth, no mis-stitch, by matcher construction.) HUD clicks work without stealing focus (non-activating).
   - Finish gestures: click Done, or press the finish hotkey — a **session-scoped Carbon-registered hotkey** (same registration mechanism as the global capture shortcut in `HotKeyController.swift`), registered when scroll mode starts, unregistered at teardown. Uses the mode's shortcut (⌃⌥⇧S); if Carbon registration fails (collision), the session continues with HUD-only finish and the HUD says so. Cancel: click Cancel. Return/Esc are deliberately NOT finish/cancel keys (keyboard focus belongs to the app being scrolled).

4. **Capture loop — `ManualScrollCaptureEngine`** (new file, sibling of `ScrollingCapture.swift`):
   - Timer loop (~150 ms cadence, injectable `Settle`/clock like `ScrollingCaptureEngine`): capture the region each tick via the existing `ScreenshotCapturing` protocol + `CaptureGeometry` crop math, at the display's native pixel scale.
   - Skip unchanged frames cheaply (downsampled luminance compare). The sampling primitives (`LuminanceSample` etc.) are currently private to `ScrollingCapture.swift` — extract them into a shared internal utility so both engines use one implementation.
   - **Viewport-tracking match model** (new `FrameShiftMatcher` wrapping the existing correlation core — replaces any crop-range/edge-frame bookkeeping):
     - Everything lives in one logical stitched coordinate space (full-res pixel rows), **top-down: row 0 is the visual top, rows grow downward**. This convention governs ALL matcher, viewport, extent, strip, and budget math. Conversion to Core Graphics' bottom-up pixel coordinates happens ONLY inside a single tested helper at the `CGImage` crop/compose boundaries. The seed occupies `[0, seedHeight)`. The session tracks `viewportOffset` (stitched-space row of the current viewport's top; starts 0) and the stitched **extent** `[top, bottom)` (starts `[0, seedHeight)`).
     - For each changed frame `F`, `FrameShiftMatcher.shift(from: previousFrame, to: F)` returns one signed vertical shift `s` in pixels (positive = content scrolled down / viewport moved down), or `nil`. Same single-clear-peak and confidence (≥ 0.92) rules as `FrameStitcher`; two candidate peaks within the ambiguity margin → `nil` (no tie-breaking — reject). `s = 0` (frame changed but content position identical — spinner, video, cursor) → in-place content change: no stitch, and `previousFrame` is NOT replaced — the stable reference frame is kept until an accepted nonzero shift, so animated content cannot poison subsequent comparisons.
     - On a match: `viewportOffset += s`; `previousFrame = F`. Novel rows = the parts of `[viewportOffset, viewportOffset + frameHeight)` outside the extent: below `bottom` → append strip to the down store, `bottom` grows; above `top` → append strip to the up store, `top` shrinks. Rows inside the extent are never re-appended — direction reversal and scrolling back over captured content (including the seed) are no-ops by construction, no clamping rules needed.
     - Tests: down-only; up-only; up→down→up; return across the seed adds zero rows; ambiguity → `nil`; in-place content change (spinner) does not corrupt `viewportOffset`.
   - **Mid-session target monitoring (pause gate)**: the session retains the resolved target **window ID**. Roughly once per second (every ~7th tick) a cheap window-list query validates the window still exists and still intersects the capture rect. On invalidation, stitching PAUSES: ticks continue but frames are dropped without degraded-counter penalty, and the HUD switches to "content changed — Resume / Cancel". Only an explicit **Resume** click (which re-resolves the target under the region center) or Cancel leaves the pause — no frames are accepted while paused, so a replaced/moved window can never silently stitch unrelated content. The check is existence + intersection, NOT topmost-ness: transient overlays (dropdowns, tooltips, autofill popups) above a live target do not trigger the gate. If no target window was resolvable at Confirm (fallback path — e.g. odd canvas apps), the monitor is disabled and the person supervises visually, as before.
   - **Unmatched-frame policy (deterministic)**: unchanged frames never count. A changed frame with `nil` shift increments a consecutive-unmatched counter (reset on any accepted match) and does NOT replace `previousFrame`. Counter ≥ 20 (~3 s of changed-but-unstitchable content) marks the session degraded; HUD shows a "content not matching" hint; Done on a degraded session returns `.partial(reason: .lowConfidence)`. Zoom/resize mid-capture lands here by design.

5. **Own-window exclusion — mandatory**: frames are captured with an `SCContentFilter` that excludes ALL of TakeAShot's windows (border, HUD, anything else). Note: the current provider already excludes own windows by bundle identifier (`ScreenCaptureEngine.swift:277`); step 0 adds a **typed exclusion-support probe** on the provider protocol (with a fake-provider test) rather than relying on filter-construction failure (the initializer does not throw). Probe reports unsupported → the session fails with an explicit error before scroll mode starts — there is no "chrome outside the rect" fallback (impossible for edge-touching/full-width selections).

6. **Bidirectional stitching — one budget, one store type**:
   - Both segments use a new bounded **`StripStore`**: an append-only temp file plus in-memory strip metadata (stitched-space range, byte offset, discovery order). One store for down-strips, one for up-strips. `IncrementalImageStitcher` is NOT used by the manual engine — only its low-level write/mmap/`CGDataProvider`→`CGImage` primitives, extracted into a shared internal utility (alongside the luminance-sampling extraction). Auto engine behavior unchanged.
   - **One global budget**: a shared accounting object tracks total pixel height, width, and bytes across seed + both stores (seed counted exactly once). Limits: 30 000 px height, 8 192 px width, 128 MiB — same numeric caps as auto. Duration limit 5 min for manual via a NEW manual-specific limit-bearing error case (auto's `.durationLimit` and its "60-second" message untouched). No frame-count limit for manual (bounded by duration + bytes).
   - **Compose (at Done)**: final image = up-store strips in reverse discovery order + seed + down-store strips in discovery order — streamed file-to-file into the final buffer, never fully in RAM, then mmap→`CGImage` wrap. The compositor owns temp-file lifetime: store files are deleted only AFTER the final image file exists (or on cancel/failure). Tests assert cleanup on every terminal path.

7. **Session lifecycle — split ownership, race-free**:
   - **`@MainActor` `ManualScrollSessionController`** owns everything UI/system: HUD panel, border window, Carbon hotkey token, target-app reference, the session **generation**, the single terminal transition (`finishing` / `cancelled` / `failed`), and idempotent ownership-verified teardown (a stale session's teardown can never unregister a newer session's hotkey or remove its windows). AppKit objects and Carbon tokens never cross an actor boundary.
   - **Worker actor** owns only compute + storage: `FrameShiftMatcher` state, both StripStores, the budget, and composition. Data crossing the boundary is Sendable value types (frames/`CGImage`, shift results, progress values).
   - Done while a tick is in flight: controller sets terminal state, awaits the worker's in-flight tick (drained), then requests composition. Cancel: terminal state set, worker task cancelled and awaited, temp files removed, then UI teardown. Every progress/result callback carries the generation token; stale callbacks are dropped on the main actor before touching UI or persistence.

8. **Result path**: identical to Auto Scrolling Capture — `.completed`/`.partial(reason:)`; partial shows the existing "Use Partial"/"Discard" dialog (`CaptureController.swift:1023`); accepted image goes through `CapturePipeline.persistAndPublish` with no `AreaSelection`, so it installs directly into the editor (same as auto — deliberate consistency).

9. **Progress + diagnostics**: engine emits stitched height via a progress callback (same shape as `scrollingCaptureProgressed` in `Models.swift`); Scroll HUD binds to it, plus the degraded-session hint (step 4). Debug logging (os.Logger) records per-tick outcome: unchanged / matched-shift (signed delta + extent change) / dropped-unmatched (confidence) / in-place — so silent data loss is diagnosable.

10. **Tests** (all against fakes; no real capture — house pattern):
    - Pure logic: `FrameShiftMatcher` signed-shift semantics (down, up, ambiguity → `nil`, in-place change keeps reference frame); viewport/extent bookkeeping (return across seed adds zero rows, up→down→up); StripStore metadata + composition order; **final-pixel-order tests**: scripted distinguishable frames (TestSupport `TestImage` color assertions) composed end-to-end, asserting the finished image's actual pixel rows top-to-bottom — not just strip ranges; AppKit↔Quartz coordinate conversion helper; top-down↔CG row conversion helper; single global budget accounting (seed counted once); unmatched-counter → degraded transition; HUD placement function; exclusion-support probe against fake provider.
    - Engine (stub `ScreenshotCapturing` feeding scripted frame sequences): down-only; up-only; up then down; unchanged-frame skipping; 20-consecutive-unmatched → degraded → `.partial(.lowConfidence)` on Done; byte/pixel cap → `.partial`; seed-capture failure → clean abort; Done during in-flight tick (drained, no lost strip); cancel during tick → cleanup, no callbacks after terminal state; stale-generation callback/teardown cannot touch a newer session; Done with only seed frame → single-frame image; target-window invalidation → pause (frames dropped, no degraded penalty) → Resume re-resolves and accepts frames again; temp files deleted on every terminal path.
    - Wiring: `RecordingCaptureIntentHandler` gains `.scrollingAreaSelection`; shortcut default registration; overlay capability flag hides annotation tools for manual-scroll intent.
    - Manual QA checklist at `docs/manual-qa/manual-scroll-capture.md` (browser page, Terminal scrollback, momentum scroll, scroll past top then back, edge-touching selection, second display, hotkey collision fallback).

## Key decisions & tradeoffs

- **Manual mode alongside auto**, not replacing it — auto covers hands-free AX-scrollable windows; manual covers regions, canvas apps, custom scrollers.
- **Polling + overlap Stitch, no event tap** — no Input Monitoring permission, momentum-scroll safe; costs ~7 fps sampling while active (bounded, capture-session only).
- **Reuse `FrameStitcher`/`IncrementalImageStitcher` core** — matcher and mmap appender are shipped and tested; new code is the loop, direction dispatch, and two-segment composition only.
- **Finish via HUD/session-scoped Carbon hotkey, not Return** — keyboard focus is in the scrolled app during capture; stealing keys would require an event tap. SwiftUI `.keyboardShortcut` cannot fire while another app is frontmost, hence Carbon registration for the session.
- **Viewport-tracking model over edge-frame/crop-range bookkeeping** — one signed shift per frame pair plus a stitched extent makes reversal, return-over-captured, and dedupe fall out of the coordinate math instead of special-case clamping rules.
- **StripStore for both segments under one budget** rather than integrating with `IncrementalImageStitcher`'s private contiguous file — the auto stitcher stays untouched; manual reuses only extracted low-level primitives.
- **Own-window exclusion is mandatory, not best-effort** — edge-touching selections make "chrome outside the rect" geometrically impossible; a session that cannot exclude its own windows fails explicitly rather than polluting the stitch.

## Risks / open questions

- Step 0 verifies `SCContentFilter(display:excludingWindows:)` through the current provider before anything else is built; if macOS 14 behaves unexpectedly here, the feature blocks on that spike (no silent fallback exists by design).
- `FrameStitcher` chrome-row detection was tuned for whole windows; user-chosen regions usually exclude sticky chrome, but a region that includes a sticky header will have those rows treated as stable chrome — expected to work, verify in manual QA.
- **Requirement bound, not just a risk**: manual capture requires overlap-preserving scrolling — a fast flick can move content farther than one viewport between 150 ms samples, producing unmatched frames → degraded hint on HUD → `.partial` on Done. Accepted v1 limitation; the explicit future upgrade path is continuous `SCStream` capture (60 fps frame history) to reconstruct skipped positions.

## Out of scope

- Changes to Auto Scrolling Capture (engine, picker, shortcut).
- Quick Annotation during scroll mode; PostCapturePanel for scrolling captures.
- Horizontal stitching; event-tap scroll detection; auto-detecting scroll end.
