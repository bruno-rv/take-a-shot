# Plan: Quick Annotation — Flameshot-style toolbar on the Selection Overlay
_Locked via grill-with-docs — by Claude + Bruno. Terms per CONTEXT.md. Rev 5 after Codex round 4._

## Goal
During area capture, after the user commits a selection rectangle on the Selection Overlay, a compact toolbar appears next to the selection offering annotation tools (arrow, text, highlight, blur, rect/ellipse outline, Step Badges, emoji). The user applies Quick Annotation directly on the live screen, then Confirms; the capture is Baked with the annotations so no editor visit is required. If the user does open the editor, it receives the same Annotation Document with every item still editable.

## Approach

1. **New annotation types** in `CaptureModels.swift`, extending the existing `AnnotationItem` enum (normalized 0–1 coords, Codable, same pattern as `ArrowAnnotation`/`RectAnnotation`):
   - `ShapeAnnotation`: rect or ellipse **outline** (`kind: .rect|.ellipse`, stroke color, stroke width). Distinct from the filled `RectAnnotation` used by highlight/blur.
   - `StepAnnotation`: center point + number. **Fixed-size badge** (diameter = fixed fraction of the image's min dimension, so Retina/export scale falls out of image size): no resize handles in the editor, hit-testing uses the computed bounds. Numbering = 1 + max existing step number in the document (renumber on delete is out of scope). **Constant style** (fixed accent fill, white numeral) — no persisted color; the color swatches are disabled while the Steps tool is active.
   - Emoji: reuse `TextAnnotation` (an emoji is a glyph); the emoji tool inserts a `TextAnnotation` with the chosen emoji and a larger default font size. No new type.
   - The 0–1 clamping contract of `NormalizedPoint`/`NormalizedRect` is **unchanged**; the Annotation Document never holds out-of-range geometry (see §5 for what happens to out-of-selection draft items).
2. **Renderer**: refactor `AnnotationRenderer`'s private per-item drawing into shared CGContext **render primitives** (stroke arrow, text run, filled/blurred rect, outline shape, step badge) that take geometry in target-space points plus a style. Two thin adapters own the coordinate transforms:
   - **Document adapter** — existing `render(source:document:)` bake path: normalized → image pixels (unchanged behavior).
   - **Draft adapter** — Selection Overlay `draw(_:)`: display-global draft points → overlay view coords.
   Teach the primitives `ShapeAnnotation` + `StepAnnotation` styles; emoji comes free via the text primitive. Pixel-alignment covered by tests (§10).
3. **Editor parity**: add rect/ellipse, steps, and emoji tools to `AnnotationTool` + `MacToolbar` + `AnnotationEditor` hit-targets/handles, following the arrow tool's pattern (create by drag — steps/emoji by click, select/move/delete, undo via existing `AnnotationHistory`). Step Badges: move only, no resize (§1).
4. **Shared palette**: extract the color palette currently private to `MacInspector` (`MacContentView.swift`) into a shared definition (with accessibility labels) used by inspector, editor, and overlay toolbar.
5. **Overlay annotation draft**: `SelectionOverlayView` gains an annotation mode with items held as an **`OverlayAnnotationDraft`** — unclamped, display-global point coordinates (matching `AreaSelection.rect`'s global-coords convention). The draft is pre-capture working state only; it is never persisted.
   - Items keep their screen position while the selection is moved/resized (no stretching).
   - **Out-of-selection semantics (per-type, at Confirm)**: filled highlight/blur rectangles are **intersected** with the final selection rect (well-defined semantics); arrows, text, outline shapes, and Step Badges are **kept only if fully inside** — partially- or fully-outside ones are dropped (generic clamping would corrupt them: moved endpoints, reflowed text, redrawn borders). The overlay previews the rule live: items that will survive render at full opacity, items that will be dropped render dimmed, highlight/blur rects show only their surviving intersection at full opacity. Nothing out-of-range ever enters the Annotation Document (0–1 contract unchanged).
   - Selection resize/move is **clamped to the owning display's bounds** (also fixes the existing possibility of dragging a rect that `ScreenCaptureEngine` later rejects as out-of-bounds).
   - Drawing: when a drawing tool is active, mouse drags create draft items instead of moving/resizing the selection (Select/Move tool restores current behavior). Overlay `draw(_:)` renders draft items via the draft adapter (§2). Cmd+Z pops the last draft item (simple stack pre-capture; full `AnnotationHistory` only in the editor).
   - **Text/emoji input**: click places an `NSTextField` field editor at the click point; commit on Enter/focus-loss becomes a draft text item. Emoji tool places the chosen emoji directly (fixed small palette popover, no macOS picker). While a field editor or popover is active, Return commits the text (not the capture).
6. **Keyboard/mouse precedence** (single deterministic chain in `SelectionOverlayView.keyDown` + field-editor delegate):
   - Active text field or popover → Esc cancels it, Return commits it. Nothing else fires.
   - Otherwise → Return Confirms; **double-click Confirms only while the Select/Move tool is active** (in drawing tools a double-click is just two clicks of that tool); Esc cancels the **entire area-capture operation on all displays** (existing behavior — Esc never "hands off" to another display; to select elsewhere, press Esc and re-invoke capture).
   - Documented in the README shortcut table.
7. **Multi-display ownership**: `ScreenCaptureController` owns an explicit *active display* state. The first overlay to commit a selection rect claims ownership for the remainder of the operation; the controller broadcasts this to all overlays — non-owning overlays clear any partial rect and ignore selection input (dimmed scrim only). There is **no ownership transfer or release mid-operation**: ownership ends only when the operation ends (Confirm, Esc, or toolbar Cancel — all of which tear down every overlay). Toolbar, annotation, and Confirm exist only on the owning display.
8. **Toolbar**: a small `NSHostingView`-wrapped SwiftUI toolbar inside `SelectionOverlayWindow`'s content view, appearing once a selection is committed. Buttons: Select/Move, Arrow, Text, Highlight, Blur, Rect, Ellipse, Steps, Emoji, shared color swatches (§4), Undo, Cancel, Confirm. Placement comes from one **pure, unit-tested function** `toolbarFrame(selection:toolbarSize:visibleBounds:) -> CGRect` operating **entirely in overlay-local (view) coordinates** — the caller converts the display's `visibleFrame` to overlay-local space once before calling; the result is used directly as the hosting view's frame. Rules: prefer below the selection; flip above if no room; if neither fits (selection reaches display edges) place inside the selection's bottom edge; always clamped horizontally and vertically into the visible bounds; covers tiny, corner, edge, and full-display selections (a toolbar wider than a tiny selection simply center-clamps within the visible bounds, overlapping outside the selection is fine). Safe in every case — the overlay window hides before capture, so the toolbar can never appear in the captured pixels. The hosting view is confined to the toolbar's frame so it never intercepts drawing/selection mouse events outside itself.
9. **Confirm flow** (`SelectionOverlayView.confirm` → `ScreenCaptureController.completeAreaSelection`):
   - **One canonical selection, both spaces**: a `CanonicalAreaSelection` value is computed once at Confirm, holding the **integral display-local `sourceRect`** (exactly what `CaptureGeometry.sourceRect` produces — origin-subtracted, Y-flipped, integralized) **and its inverse-transformed global `selectionRect`**. Capture uses `sourceRect`; the draft→normalized conversion uses `selectionRect` (same pixels, global AppKit space); preview alignment and tests use the pair. Round-trip tested on offset secondary displays.
   - At Confirm the overlay converts the draft per §5 against the canonical rect into a **`PendingAnnotationPayload`** (normalized `[AnnotationItem]`, no ID — `CapturedImage.id` does not exist yet). The draft type itself never leaves the overlay.
   - `completeAreaSelection` hands selection + payload to **`CapturePipeline.captureArea`**, which owns the whole sequence in order: capture returns `CapturedImage` → construct the `AnnotationDocument` from the payload with the fresh `image.id` → render Baked thumbnail/preview via the document adapter **off the main actor through the existing `DetachedAnnotationRenderService`** (`CapturePipeline` is `@MainActor`; a synchronous full-resolution bake — especially blur — would freeze the UI; only persistence coordination and publication hop back to `MainActor`) (raw-image thumbnail when the payload is empty; the raw original is always retained unmodified) → **atomically persist** image + document + thumbnail through the extended transactional `persist(image:annotations:thumbnail:)` in `CaptureLibrary` → only then publish that exact document with the capture. `receiveCapture` consumes the published document instead of creating an empty one. Empty payload ⇒ behavior identical to today. No post-publication async attachment.
   - **Post-capture panel**: `AppRuntime` passes the Baked preview (or the document alongside the raw capture) so the panel's preview, Copy, and Save all use the same Baked render — never the raw `capture.image` when a document exists.
   - Editor (if opened) loads the same persisted document — items editable.
10. **Tests** (extend existing targets):
    - `CaptureGeometryTests`: draft→normalized conversion against the canonical integral rect (moved/resized selection; per-type rules — filled rects intersected, arrows/text/outlines/badges fully-inside-or-dropped; fractional selection coords), display-bounds clamping of selection resize, `toolbarFrame` placement (overlay-local contract) for tiny/corner/edge/full-display selections.
    - `AnnotationModelTests`: `ShapeAnnotation`/`StepAnnotation` round-trip, step auto-numbering, payload→document binding with the post-capture `image.id` (no empty-document overwrite), Esc/Return/double-click precedence state machine (extracted as testable logic), multi-display ownership transitions (claim/deny/teardown).
    - `ImagePipelineTests`: render primitives draw shape/step/emoji (non-empty diff vs. base), draft-adapter vs document-adapter alignment for identical items, badge scale rule at 1x/2x.
    - `CaptureLibrary` tests: atomic persist of image+document+Baked thumbnail; failure rolls back (no image without its document); publication only after commit; **reopen durability** — persist → fresh store instance → load image + document → document identity matches and Baked thumbnail pixels differ from raw when annotations exist.
    - **Baked panel path**: injected-seam test on the `AppRuntime`→`PostCapturePanel` presentation verifying preview, Copy, and Save all receive the Baked render/published document (not raw `capture.image`) when a document exists; mirrored as a manual checklist scenario.
    - **Manual QA checklist** checked in at `docs/manual-qa/quick-annotation.md` with enumerated scenarios and expected results: field-editor focus in the borderless `.screenSaver` window; Enter/Esc/focus-loss on text entry; emoji popover open/dismiss; toolbar hit-confinement (drawing works adjacent to toolbar edge); placement extremes (tiny/corner/full-display selection); 1x vs 2x displays; multi-display claim/deny + Esc teardown. Each run records pass/fail per scenario in the PR description.

## Key decisions & tradeoffs
- **One annotation system, two surfaces** — shared render primitives with draft/document adapters instead of a parallel implementation. See docs/adr/0001 (updated).
- **Annotations stay editable** — Bake is for outputs only; the document travels with the capture, persisted atomically with the image. Satisfies "apply directly, no editor needed" and "editor carries the edits" simultaneously.
- **Out-of-selection draft items are dropped/clamped at Confirm, previewed live** — keeps the 0–1 document contract untouched; "recoverable outside the crop" rejected as a schema change with no user demand.
- **Blur is cosmetic, not redaction** — the original pixels are retained in the library and the document is editable, so blurred content is recoverable by design. The blur tool's help text states this. True irreversible redaction is a separate feature, out of scope.
- **Emoji = TextAnnotation**, **Step Badges fixed-size** — no new geometry machinery where reuse or a constant suffices.
- **Toolbar is hosted SwiftUI inside the AppKit overlay window** — smallest bridge; porting the overlay to SwiftUI rejected (high risk, zero user value).
- **Blur preview pre-capture is a placeholder** (frosted rect) since real pixels aren't available until capture; actual blur appears in the Bake and everywhere after.

## Risks / open questions
- Field-editor focus inside a borderless `.screenSaver`-level window — activation-order fix (c1ba661) should cover it; manual checklist verifies.
- `NSHostingView` event routing vs. the overlay's mouse handling — mitigated by confining the hosting view to the toolbar frame; manual checklist verifies.

## Out of scope
- Cloud upload (removed), animated GIF stickers, full macOS emoji picker, renumbering Step Badges on delete, irreversible redaction, out-of-crop annotation recovery, annotation on window/fullscreen/scrolling captures (area only for v1), toolbar customization, AppKit UI test harness.
